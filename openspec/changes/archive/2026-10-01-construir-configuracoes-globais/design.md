# Design

## Context

O shell administrativo (`app/layouts/admin.vue` + `AppHeader`/`AppSidebar`) já está no modelo final (change `adotar-shell-claro-escuro`, arquivado) e todas as rotas `/admin/**` herdam shell automaticamente. `app/config/navigation.ts` é a fonte única de navegação (spec `layout-navigation`), mas `SidebarItem`/`MenuItem` não têm noção de rota — `AppSidebar` só faz `itemAtivo = item.id` e `AppHeader` só fecha o menu. O kit `app/components/ui/` tem 19 componentes, nenhum de navegação segmentada (abas) nem de intervalo (slider); `main.css` já hospeda utilitários `.ds-*` (recorte de foco, hovers) servido graças ao `tailwindcss.cssPath`. A vitrine `/design` tem 15 seções e docs/01 §5 documenta cada componente na numeração da vitrine. Ver `proposal.md` para motivação e escopo.

## Goals / Non-Goals

**Goals:**
- Dois componentes de kit reutilizáveis (`UiTabs`, `UiSlider`) com contrato ARIA/teclado consistente com o restante do kit (v-model + `change` com valor, foco `#1a9e07`).
- Tela `/admin/configuracoes-globais` fiel ao mockup, com a aba de retenção funcional em estado em memória.
- Navegação sidebar/Account com rota opcional, sem quebrar os 9 itens que continuam sem rota.
- Vitrine §16 + docs/01 §5.13–§5.14 + docs/03 §11 no mesmo change (regra AGENTS).

**Non-Goals:**
- Backend, persistência, `sistema_config`, auth/RBAC (já declarados fora de escopo na proposal).
- Componente `UiAlert` — o banner informativo é markup de domínio (decisão do usuário: só `UiTabs` e `UiSlider` entram no kit).
- Rotas para os demais itens da sidebar.

## Decisions

**D1 — Abas como componente controlado (`v-model` + `change(id)`), painéis ficam na página.**
`UiTabs` é só o tablist; cada painel é renderizado pela página com `v-if` e `role="tabpanel"`/`aria-labelledby`. Alternativa considerada: componente com slots nomeados por aba (mais encapsulado), descartada porque os painéis têm vidas próprias (o domínio `AbaRetencaoAuditoria` é um componente à parte) e slots nomeados impediriam `v-if` simples. O padrão de eventos segue docs/01 §4.2 (`change` emite valor, nunca `Event`).

**D2 — Teclado via handler no tablist com roving focus.**
`←`/`→` com wrap-around, `Home`/`End`; a aba selecionada recebe foco (uma aba focável por vez via `tabindex`, demais `-1`), espelhando o padrão de roving tabindex já usado no `Calendar` (docs/01 §5.8). `useId()` liga `aria-controls`/`aria-labelledby` entre tab e painel.

**D3 — Slider = `<input type="range">` nativo + CSS `.ds-slider` em `main.css`, sem pseudo-elementos de thumb no Tailwind.**
O `::-webkit-slider-thumb`/`::-moz-range-thumb` não é estilizável por classes utilitárias; por isso o estilo vive em `main.css` (arquivo já servido, `form-control-states` exige que regras próprias estejam no CSS). Preenchimento da track via CSS var `--pct` calculada no componente (`((value - min) / (max - min)) * 100%`) em degradê **`#112051` → `#0364f7` → `#4ed813`** esticado da origem até o thumb (pedido do usuário; `--pct` define onde o degradê termina e `calc(var(--pct) / 2)` posiciona o azul no meio da região preenchida), resto `slate-200`. Alternativa descartada: divs customizadas no lugar do input (perderia o comportamento nativo de teclado/ARIA do range). Foco: `:focus-visible` com outline `#1a9e07` (requisito do spec `slider`; consistente com `form-control-states` §2.2).

**D4 — `marks` renderiza legenda em `justify-between` sob a track; `aria-valuetext` vem de prop `valueText` com default `"{n} dias"`.**
A legenda é informativa (não interativa) — clicar nela não move o slider (fora do mockup). O texto acessível "180 dias" satisfaz o cenário do spec sem acoplar o componente a "dias": o consumidor pode passar `value-text` próprio. Decisão registrada: no mockup a legenda está em `justify-between` (5 rótulos distribuídos), não posicionada por % do valor — o componente segue o mockup.

**D5 — Seleção única dos atalhos no domínio, com `UiCheckChip variant="slate"` e `showCheck=false`.**
O `CheckChip` já tem exatamente a pill ativa navy (`bg-brand-primary border-brand-primary text-white`) exigida pelo mockup; falta só suprimir o ✓ — daí a prop `showCheck` (default `true`, back-compatível com os 2 usos existentes na vitrine §11). Single-select é lógica do painel (`:model-value="dias === n"` + `@change="v => v && (dias = n)"`): clicar no chip ativo emite `false` e é ignorado, mantendo sempre um valor vigente. Alternativa descartada: novo `UiRadioChip` (mais um componente no kit para o mesmo visual).

**D6 — `itemAtivo` da sidebar passa a derivar da rota quando há correspondência; fallback no estado local.**
`AppSidebar` ganha `useRoute()`; um `computed` resolve `route.path` → id do item (pelo campo `to`), e itens sem `to` seguem usando o ref local como hoje. Isso faz URL direta marcar o item (cenario do spec `layout-navigation`) e evita dessincronia (estar na rota com outro item destacado). Clique: `if (item.to) navigateTo(item.to)` — `navigateTo` é auto-import do Nuxt. O menu Account ganha o mesmo `to` e navega + fecha menus. `navigation.ts` ganha `to?: string` em `SidebarItem` e `MenuItem` (interface, sem quebra) e `to: '/admin/configuracoes-globais'` nos 2 itens "Configurações Globais". A vitrine §14 importa os mesmos dados — com `to` presente, o clique lá também navega (aceitável: é o mesmo shell espelhado); se a demo da vitrine não quiser sair da página, o handler de `to` na vitrine é inibido — ver Open Questions.

**D7 — Página fina com 6 componentes de domínio; estado na página e nos painéis.**
`configuracoes-globais.vue` só compõe e guarda o estado global (`aba` com default `logomarcas` por pedido do usuário, `diasRetencao`, flag `alterado` do botão Salvar); as partes viram componentes em `app/components/configuracoes/` (exigência docs/01 §2.2, ajuste do usuário): `Cabecalho.vue` (cabeçalho **sem container**, `UiButton size="md"` à direita, emite `salvar`, recebe `desabilitado`), `Abas.vue` (container card único — barra de abas + área do `role="tabpanel"` no slot; define as 4 abas), `AbaRetencaoAuditoria.vue` (conteúdo puro, recebe/emit `dias` por `v-model`), `AbaLogomarcas.vue`, `AbaSidebar.vue` e `AbaSeguranca.vue` (cada um guarda seu próprio estado em memória — URLs, seleções e registros, emitindo `change` quando alteram). Os painéis vivem dentro do container: sem card de header e sem cards aninhados. Alternativa descartada para o estado de tela: `useState`/composable global (overkill para estado em memória de uma tela) — **ressalvas**: a logo do header e as sessões do menu precisam viver fora do componente (o `AppHeader`/`AppSidebar` são do shell), daí os composables `useLogomarcaHeader` e `useSessoesAbertas` (ver D12). O antigo `AbaEmBreve.vue` foi removido quando as 3 abas restantes ganharam conteúdo.

**D8 — Conteúdo da aba de retenção idêntico ao mockup, com `<code>` inline.**
Subtítulo, query e o grande "180" derivam de `dias`. A query usa `INTERVAL {{dias}} DAY` interpolado. Verde do número grande: `text-[#0f7a06]` — a regra docs/01 §2.1 reserva `#1a9e07` para foco/bordas e `#0f7a06` para **texto** verde sobre superfície clara (o mockup mostra o número em verde; nenhum hex divergente). Tipografia: `font-mono font-bold tabular-nums` (precisão numérica obrigatória). O banner é `bg-blue-50 border-blue-200` com ícone `Info` — chrome de aviso azul já usado no kit (§8 da vitrine usa sky/blue em avisos); sem token novo.

**D9 — Botão "Salvar" = `UiButton variant="primary" size="md"` com `leftIcon` Save em `text-brand-accent`; nasce desabilitado.**
Degradê do `primary` é o caminho canônico (`brand-tokens`: degradê só em botão primário e header de modal). Ícone accent sobre o degradê navy passa no contraste. Toast via `useToast().success` (docs/01 §4.6). Tamanho `md` (e não `lg`) por pedido do usuário na conferência. **Dirty flag** (pedido do usuário): o botão recebe `:disabled="!alterado"` (`Cabecalho` expõe a prop `desabilitado`); `alterado` nasce `false`, cada painel emite `change` via `watch` sobre seus refs locais (retenção: watch no `v-model`), a página liga `@change="alterado = true"` e `salvar()` reseta a flag — alternativa descartada: habilitar só o painel visível (o pedido é "qualquer funcionalidade alterada", inclusive de abas já visitadas).

**D10 — Vitrine §16 espelha os componentes reais, seguindo o padrão das seções 3–13.**
Uma seção "16. Tabs & Slider" com demo funcional dos dois (aba interativa + slider com marcas e readout), índice `secoes` atualizado. Docs/01 ganha §5.13/§5.14 e o sumário é atualizado; §5.9 ganha nota do `showCheck`. Ordem: como `design.vue` numera as seções, a 16 entra após a 15 (Modal) — sem renumeração.

**D11 — Pill ativa do `UiTabs` em estilo lime (referência do usuário).**
A pill ativa usa `bg-lime-50 border-lime-300 text-lime-900` com `hover:bg-lime-100` — o mesmo padrão do chip lime ativo/`Button accent` — e as inativas ficam com borda transparente para não haver salto de layout na troca. Duas alternativas foram descartadas pelo usuário na conferência: fundo sólido `bg-brand-primary` e degradê igual ao `Button` `primary`; com a pill lime o degradê permanece restrito a `Button` `primary` e header do modal (`brand-tokens` sem alteração).

**D12 — Três painéis novos reusam o kit; desvios pontuais seguem o mockup e são markup de domínio.**
Mockups enviados pelo usuário definem o conteúdo de Logomarcas, Sidebar e Segurança. Regras: (a) **seleção única da barra lateral via `UiCheckCard variant="slate" checkbox-position="start"`** — decisão explícita do usuário ao ser informado de que o kit não tem rádio (em vez de criar `UiRadio`/`UiRadioCard`); o padrão de single-select é o mesmo dos atalhos de retenção (`:model-value` derivado + `@change` só aplica quando `true`), na revisão os cartões ganharam os recursos ricos do componente (`badge` + `:icon`, como na vitrine §15), perderam as linhas de referência das colunas e a opção não selecionada de cada grupo ficou atenuada (`opacity-60`, pedido do usuário — visual "desativado" sem bloquear o clique); **sessões do menu passaram a ser múltiplas + presets** (pedido do usuário, decisão confirmada em Q&A): o card tem os presets globais "Todas Abertas"/"Todas Recolhidas" (aplicam em tudo quando marcados) e, na coluna ao lado, um cartão por sessão (Publicações · Cadastros · Administração, com badge dinâmico `Aberta`/`Recolhida` e descrição = itens da sessão) marcável/desmarcável de forma independente — estado misto deixa os dois presets desmarcados; o estado mora nos composables `useSessoesAbertas` (`useState<Record<label, boolean>>` com default vindo de `navigation.ts`) e `useSidebarExpandida` (`useState<boolean>`, default `true` — o `admin.vue` deixou de ter `ref` local e passa a ler a preferência, então o toggle do header escreve na mesma fonte) e o `AppSidebar`/layout admin os leem como fonte única (`sessoes` vira `computed`, `alternarSessao` escreve de volta), então a preferência reflete em tempo real na sidebar real e os cliques no shell atualizam a preferência (mesma semântica de espelho da logo no header); layout: os dois containers do painel ficaram empilhados em coluna única e cada um com o conteúdo em duas colunas (`grid md:grid-cols-2` — presets à esquerda, sessões à direita), pedido do usuário na conferência; (b) **aba Logomarcas usa `UiUploadFiles`** (pedido do usuário): enviar arquivo grava o caminho `/uploads/logomarcas/<nome>` no campo `UiInput mono` e alimenta a prévia da caixa de upload; dois estados distintos — `preview*` (dataURL para exibição — trocada de objectURL para dataURL quando a logo passou a refletir no `AppHeader`, porque a objectURL é revogada no unmount e a prévia precisa sobreviver à troca de aba) e `logo*` (caminho gravado), com remontagem da caixa (`:key`) ao limpar para não sobrar prévia órfã; **reflexo no shell**: o composable `useLogomarcaHeader` (`useState` de caminho + preview) sincroniza o painel com o `AppHeader` por watch — ao definir a logo, o header exibe `<img>` no lugar do ícone + "Publications"; ao limpar, a marca padrão volta; o painel é inicializado a partir do mesmo estado (reentrar na aba restaura badge/prévia/caminho), descartando a alternativa de manter objeto/URL só local no painel (ficaria dessincronizado do shell); sem seção de pré-visualização dark e sem botões de modelo (removidos a pedido do usuário na revisão); badge de status por card e todos os controles do kit; (c) **lista de bloqueios no `UiDataTable` do kit e cards de indicadores em markup de domínio** — pedido do usuário: os registros bloqueados são exibidos no `UiDataTable` padrão (cabeçalho navy, Group By Box, ordenação, paginação, busca via `show-header-top`) com coluna **Ações** via slot `actions` (`UiTooltip` envolvendo **apenas o ícone** `LockOpen` em botão transparente sem moldura — `UiButton` e texto removidos a pedido do usuário —, com `aria-label`) e slots de célula para IP em mono, badge `blocked` de tentativas e motivo truncado; a coluna "Identificador / E-mail" ficou com `minWidth: 170` para não gerar barra de rolagem horizontal; os cards de indicadores continuam markup de domínio porque `UiKpi` traz ondas animadas e borda colorida que divergem dos cards planos do mockup; os **controles** seguem do kit (`UiButton`, `UiBadge`, `UiInput`); (d) ações em memória: liberar remove a linha e atualizar só confirma por toast — os botões "Simular Bloqueio Teste" e "Limpar Todos" do cabeçalho foram removidos a pedido do usuário (sem funções mortas); (e) espaçamento cabeçalho→container em `mt-10` (40px) por pedido do usuário (+1cm e depois −0,5cm na conferência).

**D13 — No modo rail, o recolhimento das sessões não esconde ícones (bug do usuário, task 6.35).**
Com "Todas as Sessões Recolhidas" + sidebar recolhida, o rail ficava só com o ícone raiz — `AppSidebar` gateava os itens do rail em `sessao.aberto` e a vitrine §14 filtrava `sessoesVisiveis` no rail, refletindo a requirement antiga da spec `layout-navigation`. Decisão: **o acordeão vale apenas no modo expandido**; o rail é uma lista achatada de **todos** os ícones com divisor entre sessões (sem cabeçalhos, com tooltip por item), e o estado `aberto` segue preservado ao reexpandir. Alternativa descartada: esconder também no rail (era o bug — deixa o rail quase vazio e nega o acesso rápido que ele existe para oferecer). Mudança de comportamento entra na change como substituição do requisito de rail via delta `REMOVED` + `ADDED` (título novo "A sidebar alterna entre modo expandido e rail exibindo todos os ícones e preservando o estado", cenário "Rail mostra todos os ícones mesmo com todas as sessões recolhidas" — o OpenSpec não aceita renomear cenário dentro de `MODIFIED` e o nome antigo "Rail mostra apenas ícones de sessões abertas" contradiz o novo comportamento); vitrine §14 espelha o mesmo ternário.

## Risks / Trade-offs

- [CSS de thumb do range varia entre browsers (webkit/moz)] → implementar ambas as variantes pseudo-elemento em `main.css` e conferir em Chrome + Firefox na etapa visual; fallback aceitável: thumb default com cor herdada.
- [`.ds-slider` pode ser esquecida fora do CSS servido] → `form-control-states` já garante que `main.css` é servida (`.ds-bottom-clip` é o canário); a task de build confere a presença da regra.
- [Vitrine §14 pode passar a navegar de verdade ao clicar no item (com `to`)] → inibir navegação no handler da demo se a conferência visual mostrar indesejado (Open Question abaixo).
- [`CheckChip` com `showCheck=false` reduz affordance de "selecionado"] → a pill navy cheia já comunica seleção (mesmo código visual do mockup); se a conferência visual achar ambíguo, reavaliar com o usuário sem mudar spec.
- [Estado em memória "perde" dados ao recarregar] → é comportamento exigido pelo spec (`Estado não persiste`); documentado como fase 1.
- [Sem lint/test/typecheck no projeto] → `npm run build` + SSR + conferência visual continuam sendo o gate (AGENTS.md).

## Migration Plan

Sem migração de dados ou de rotas existentes (rota é nova). Rollback = reverter os arquivos do change; nenhum consumidor externo quebra: `to` é opcional, `showCheck` tem default, componentes são aditivos. Deploy segue o fluxo normal (`npm run build`).

## Open Questions

- **Clique no item da sidebar dentro da demo §14 da vitrine:** com `to` em `navigation.ts`, a demo (que importa os mesmos dados) também navegaria. Manter a navegação (espelho fiel do shell real) ou inibir na vitrine? Não muda specs nem tasks — decide-se na conferência visual.
- **Ícones/coloração das 4 abas:** o mockup sugere tons (âmbar, azul, verde, rose). Cores exatas a confirmar na conferência visual; nenhuma spec depende delas.
